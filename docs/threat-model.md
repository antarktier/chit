# Threat model

Chit protects the payment instructions a merchant signs and the evidence that a payer settled them. The assets are the payer's funds and wallet credentials, the merchant's signing phrase and registered ML-DSA-87 key, the request and payment records in D1, the Worker attestation seed, and the chain transactions behind receipts. ChitPay forwards funds to the recipient within the payment transaction. Native QoreX sends go directly to the recipient.

Potential attackers include someone distributing fake invoices, a payer or bot submitting false evidence, a malicious wallet or dependency, and anyone who gains control of the app origin, Cloudflare account, database, or chain endpoint. Honest clients can also submit twice, and network outages or indexing delays can make views disagree.

## Browser and payment links

The payer crosses from an invoice or message into the Chit website. The page then reads the signed request from the Worker and the merchant key from Diana.

| Threat                                                          | Mitigation and remaining risk                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                   |
| --------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Tampering with the recipient, amount, reference, or description | The browser and Worker recompute the request ID and details hash and verify the merchant signature against the registered, possession-proven key. ChitPay checks the signed instructions on the first payment and transfers to the signed recipient. A compromised browser or app origin can still misrepresent what it displays. [Request encoding](../packages/core/src/request.ts) · [Pay page](../app/src/pages/Pay.tsx) · [API](../service/src/api.ts) · [Contract](../contracts/src/ChitPay.sol)                                                                                          |
| Phishing and lookalike requests                                 | The pay page shows the recipient, merchant key, reference and amount for comparison with the original invoice. A valid signature proves control of the registered signing key. The payer still needs a trusted source for the merchant's address and the Chit URL. An attacker can sign a convincing invoice with their own key or host a fake pay page. [Pay page](../app/src/pages/Pay.tsx)                                                                                                                                                                                                   |
| Merchant key loss or theft                                      | The merchant can back up the recovery phrase and choose whether the browser remembers it. Registration requires proof of possession. If the phrase is lost, restore from backup or issue fresh requests with a new registered key and tell payers which links to use. Anyone with the old phrase can sign as that merchant, and Chit has no link revocation. Previously authenticated ChitPay requests can still be paid until expiry or settlement. [Signing key screen](../app/src/pages/SigningKey.tsx) · [Browser storage](../app/src/signer.ts) · [Contract](../contracts/src/ChitPay.sol) |
| Client-side success spoofing                                    | Chit displays a submitted transaction separately from settlement. The Worker reads and decodes chain evidence before updating the reconciled status. A modified browser can fake a success screen or screenshot, so a merchant taking action on a payment should check the receipt and chain evidence. [Pay page](../app/src/pages/Pay.tsx) · [API](../service/src/api.ts) · [Reconciliation](../packages/core/src/reconcile.ts)                                                                                                                                                                |

## Browser and wallet extension

QoreX controls the payer's wallet and approves transactions. The app supplies the destination, amount, and native memo or EVM calldata.

| Threat                                                                                   | Mitigation and remaining risk                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                    |
| ---------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| A malicious or compromised extension signs a different transfer or lies about submission | The EVM flow checks that the native and EVM accounts match, checks the chain, and simulates the ChitPay call. Diana's EVM authorization window can restrict the target, value, transaction count and lifetime. The Worker still checks the actual transfer. A wallet with access to the payer's keys can steal funds, hide warnings, or sign outside the app. The payer must review the wallet approval. [Wallet integration](../app/src/wallet.ts) · [Diana window setup](../scripts/diana.ts) · [Chain decoding](../service/src/chain.ts)      |
| Replay or reuse across contracts, chains, or requests                                    | The signed message binds the request to Diana and to the payment contract. The contract and D1 bind a reference to one request per merchant. The contract enforces expiry, outstanding balance, and the partial-payment rule. Native transfers lack those contract checks. Separate on-chain accounting for the two routes allows a payer to overpay, and the merchant must handle refunds. [Request encoding](../packages/core/src/request.ts) · [Contract](../contracts/src/ChitPay.sol) · [D1 schema](../service/migrations/0001_initial.sql) |
| A native memo collides with or is copied from another request                            | The memo uses the full request ID, and reconciliation checks the destination, asset, amount rules, and block time. Copying a memo alone provides no credit, but anyone can send funds with a known memo. A mistaken transfer can therefore be credited to the wrong matching invoice or counted as an overpayment. [Memo construction](../app/src/wallet.ts) · [Reconciliation](../packages/core/src/reconcile.ts)                                                                                                                               |
| A token or recipient tries to alter the contract's accounting                            | ChitPay blocks reentry, rolls back accounting if transfer fails, and checks that the recipient's token balance increased by the full amount. A hostile token can misreport balances or withhold transfers. [Contract](../contracts/src/ChitPay.sol)                                                                                                                                                                                                                                                                                              |

## API Worker and D1

The Worker validates public submissions, reads chain evidence, and writes request and event records to D1. It uses a separate service seed to sign receipts.

| Threat                                                                    | Mitigation and remaining risk                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                         |
| ------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Fabricated payment reports or duplicate events                            | A submitted hash is a lookup hint. The API reads the transaction from the configured chain, checks execution and decodes the expected events. D1 deduplicates events by source, transaction hash and event index. A second real transfer has a new hash and can still overpay. [API](../service/src/api.ts) · [Chain decoding](../service/src/chain.ts) · [Indexer](../service/src/indexer.ts)                                                                                                                                                                        |
| A compromised API or database changes records or presents a false receipt | The receipt page can match the request ID, verify the merchant's signature, fetch the listed transactions directly, and recalculate the outcome. An attacker controlling the service can suppress requests or omit real payments. The browser verifies the listed evidence and depends on the chain endpoints it uses. [Receipt page](../app/src/pages/Receipt.tsx) · [Chain verification](../app/src/receipt-chain.ts) · [D1 binding](../service/src/worker.ts)                                                                                                      |
| The attestation seed is stolen or lost                                    | The seed is a Worker secret. If exposed, replace it with a fresh seed, publish the new public key through a trusted channel, and treat attestations made with the old key as suspect. The browser reads the current key from the same API, and Chit has no key history or revocation mechanism. Archive an independently trusted key if old receipts must remain verifiable. Chain verification remains a separate check. [Worker configuration](../service/wrangler.toml) · [Attestation](../service/src/api.ts) · [Receipt format](../packages/core/src/receipt.ts) |
| Denial of service or Cloudflare quota exhaustion                          | The API bounds list sizes and scan ranges, scopes native scans, and accepts a transaction hash for direct lookup. Repeated public reads or reports can still consume Worker, D1, and RPC quotas. Rate controls at the edge and monitoring for quota and index lag are operational measures. During an outage the chain can settle funds while Chit falls behind. [API](../service/src/api.ts) · [Indexer](../service/src/indexer.ts) · [Worker configuration](../service/wrangler.toml)                                                                               |
| Public payment metadata exposes private information                       | The public API exposes requests, descriptions and receipts, and merchant endpoints group requests. On-chain amounts, addresses, timing and references or memos can link transactions. Keep personal or confidential data out of descriptions and share only public-facing invoice labels. A signed link provides integrity and anyone with access can read it. [API](../service/src/api.ts) · [D1 schema](../service/migrations/0001_initial.sql)                                                                                                                     |

## Chain RPC and explorer

The Worker and browser query Diana for registered keys, transactions, and block height. Explorer links let people inspect evidence in a separate interface.

| Threat                                                     | Mitigation and remaining risk                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                    |
| ---------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| RPC lies, equivocates, or stops responding                 | The receipt page independently fetches and verifies the listed evidence and the key, and EVM execution enforces contract rules on chain. Browser and Worker queries can still rely on the same provider. A dishonest endpoint can fabricate or withhold evidence or mislead the browser about keys. For disputed payments, cross-check with a separately trusted Diana node. [Chain verification](../app/src/receipt-chain.ts) · [Service RPC](../service/src/chain.ts) · [Contract](../contracts/src/ChitPay.sol)               |
| A reorganization removes a counted transaction             | Diana uses two confirmations in Chit. The receipt page checks an EVM receipt's block hash against the current block at that height. The EVM indexer advances forward and has no automatic rollback. Native overlap helps with delayed indexing, and native verification depends on the REST response. A stale database may show a paid status after the underlying evidence changes. [Worker configuration](../service/wrangler.toml) · [Indexer](../service/src/indexer.ts) · [Chain verification](../app/src/receipt-chain.ts) |
| Explorer impersonation or misleading data                  | The UI links to the configured explorer. Reconciliation and receipt verification use chain RPC. A compromised explorer can show false details or solicit credentials, and opening its links can reveal interest in an address or transaction. [Explorer links](../app/src/chain.ts) · [Chain verification](../app/src/receipt-chain.ts)                                                                                                                                                                                          |
| A dependency, build system or wallet update is compromised | The repository tracks a dependency lockfile and separates local test keys from deployment secrets. The wallet comes from the publisher's official store. A malicious locked dependency, compromised build or stolen publishing credential can still change the code that executes or expose assets. [Lockfile](../bun.lock) · [Deployment](deployment.md) · [Wallet integration](../app/src/wallet.ts)                                                                                                                           |

## Live browser verification

`bun run test:live` creates one signed 0.001 QOR request against the deployed API and checks the displayed recipient, amount, reference and verified signature on Chit. It signs and broadcasts the EVM payment with a Diana account through a test EIP-1193 provider and checks the paid outcome in both the UI and API. The test checks for serious and critical axe findings in the pay states it visits. [Live test](../app/e2e-live/pay-live.spec.ts)

The native check loads the unpacked extension from `/workspace/tools/qorex/unpacked` or `CHIT_QOREX_DIR`. It checks the installation prompt when the extension is absent. The official Chrome build tested, QoreX 0.4.3, loaded in Playwright Chromium, exposed native signing and broadcast, and opened a wallet window from the Pay button. Coverage ends at that handoff. [Official QoreX listing](https://chromewebstore.google.com/detail/qorex/cflpnggbnnifibblifgbeobogdpfjpcg)

To complete the native check, open QoreX, create a test wallet or import a funded Diana test account, and unlock it. Switch the wallet network to Diana and select the funded account. Open a fresh unpaid Chit link, select **QoreX transfer**, and click **Pay**. Approve the connection to `chit.antarktier.com`, then review the recipient, amount, fee and `chit:` memo in QoreX before approving the transfer. Wait for Chit to show **Paid in full** and verify the native transaction in the receipt. [QoreX browser guide](https://docs.qorechain.io/qorex/browser-extension/)
